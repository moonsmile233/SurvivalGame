# 响应式 / 随画面缩放审查

> 文档版本：2026-10-31T21:30+08 · 作者：策划 · 改前必须从磁盘重读；上下文旧副本作废。
> 目的：确认“屏幕/游戏区变化时，哪些东西会跟着缩放、哪些不会”，避免只修了摇杆、别的元素漏掉。
> 依据：当前代码（`HudCanvasScaler` / `SceneSetup` / `TouchJoystickView` / `web/css/style.css`）+ 现有截图。

## 1. 三层缩放机制

| 层 | 机制 | 会不会随画面缩放 | 风险点 |
|---|---|---|---|
| Unity UI（HUD/暂停/结算/摇杆） | 同一块 `HUD Canvas` + `CanvasScaler.ScaleWithScreenSize`；`HudCanvasScaler` 在窄屏把参考分辨率 1280×720 切成 640×360 | **会**；所有 uGUI 元素用参考单位，随 Canvas 缩放 | 参考分辨率是**离散切换**（`Screen.width < 1000` 设备像素），阈值附近/极端宽高比可能选错档 |
| H5 DOM（页头/昵称/按钮/提示/结算卡） | CSS 相对单位、`aspect-ratio:16/9`、`max-width:960px`、媒体查询；按钮 `min-height:44px`（短横屏 36px） | **会**；布局随宽度/高度重排 | 短横屏按钮 36px 低于 44px 推荐值；极端 320 宽需验 |
| 游戏世界（相机/地图/精灵） | 正交相机 `orthographicSize=5` 固定；精灵是世界单位；相机跟随并钳制 | **按世界单位缩放**；画面高度对应的世界范围固定，宽高比变化只改变可见横向范围 | 不同宽高比下可见范围不同，但不应拉伸变形；地图边缘仍可见 |

## 2. 逐元素确认

| 元素 | 缩放方式 | 现状 | 证据/待办 |
|---|---|---|---|
| HP 条/数字 | Canvas 参考单位 | 会 | 390×844、844×390、768×1024、1280×720 截图可读 |
| 时间/分数 | Canvas 参考单位 | 会 | 同上 |
| 暂停按钮 | Canvas 参考单位 | 会 | 竖屏约 100×45 CSS px；横屏/平板需补 Playing 截图 |
| 暂停面板/3-2-1 | Canvas 参考单位 | 会 | 竖屏/桌面有；横屏、平板暂停面板待补 |
| 结算卡片（H5） | CSS grid `auto-fit minmax(120px,1fr)` | 会 | 390/844/1280 有；320 宽、844×390 待补 |
| 摇杆可视化 | 按 Canvas **短边 × 0.07**（M4.7 修复中） | 会；之前用 maxRadius 夹取，看起来不随屏幕变 | 修复后补 390/844/1280 三视口 + 非中心触摸 |
| 页头/昵称 | CSS 固定字号 + 媒体查询 | 会重排；字号不连续缩放 | 320/768/1280 待补 |
| 开始/重新开始按钮 | CSS `min-height:44px`（短横屏 36px） | 会 | 短横屏 36px 属高度受限折中，记录即可 |
| 加载遮罩/错误卡 | flex + max-width | 会 | 320 宽待补 |
| 地图/相机/精灵 | 世界单位 + 固定正交尺寸 | 不变形；可见范围随宽高比 | 大地图/边缘已有证据 |

## 3. 结论与待验

**已确认**：

- 整个 Unity UI 走同一个 CanvasScaler；**没有第二个元素像摇杆那样用原始屏幕像素做尺寸**。
- H5 用 CSS 相对布局与媒体查询，不是固定整页宽度。
- 世界层用世界单位，不会因为屏幕变化被拉伸。

**必须补验（M4.7 修完后一次跑完）**：

| 视口 | 检查 |
|---|---|
| 320×568（小屏） | HUD 不重叠、暂停面板可读、开始按钮不溢出、结算卡不横向溢出 |
| 390×844（竖屏） | 现有基线；摇杆修复后重截 |
| 844×390（短横屏） | HUD/暂停面板/摇杆；H5 短横屏按钮 36px 是否可点 |
| 768×1024（平板竖屏） | HUD/面板字号；摇杆大小 |
| 1280×720（桌面） | 基线；摇杆 |
| 1920×1080（大屏） | HUD 不会被拉得过大；面板居中 |

**判定标准**：

- 任何元素不重叠、不溢出、不超出安全区；文字可读（手机等效 ≥12 CSS px，按钮 ≥36 CSS px 且尽量 44）。
- 摇杆直径随 Canvas 短边等比变化（390/844/1280 三张可量）。
- 320 与 1920 不出现“元素跑到屏幕外/字小到看不清/面板被裁”。

## 4. 如果发现不达标

- **不要逐元素写死像素**。优先修 `HudCanvasScaler` 的档位判定（例如改用 CSS 像素宽度或按宽高比/短边判断），
  或调 H5 媒体查询；单个元素只在确实需要时改参考尺寸。
- 改完必须重跑上表；不接受“桌面上看着没问题”。
- 真机（Honor 90 Pro / iPhone）仍单独验：安全区、刘海、横竖屏切换。

## 5. 6 视口矩阵结果（2026-10-31 22:06，构建 1.0.0）

证据：`docs/evidence/resp-{320x568,390x844,844x390,768x1024,1280x720,1920x1080}-{playing,paused}.png`。

| 视口 | 结果 | 备注 |
|---|---|---|
| 320×568 | **通过（有一项 P2）** | HUD/暂停面板不重叠、不溢出；暂停按钮视觉高度约 27 CSS px，低于 44 推荐值，功能不受影响 |
| 390×844 | 通过 | HUD 放大后清晰；暂停按钮同样偏小（约 30 CSS px） |
| 844×390 | 通过 | 短横屏布局；H5 按钮 36px 属高度受限折中 |
| 768×1024 | 通过 | HUD/面板按参考分辨率放大 |
| 1280×720 | 通过 | 桌面基线 |
| 1920×1080 | 通过 | 游戏区限宽 960，HUD 不被拉得过大；面板居中 |

摇杆非中心测试：`m47-joystick-{mobile,landscape}-offset*.png` 红圈=真实触摸点，底座圆心重合、摇杆头在圈内；
尺寸改为 `min(canvas 短边) × 0.07` 后明显变小，且随 Canvas 变化。

**未关闭**：

- P2：320/390 上暂停按钮的**视觉**触碰高度 <44 CSS px；可选方案是加透明点击热区（不改视觉大小），
  或 compact 档位单独加大按钮；不影响交付，先记录。
- 全屏（**必做**，M4.5 §1）实现后，进出全屏会改变 Canvas 尺寸，必须重跑本矩阵（HUD/摇杆/暂停面板）。
- 真机安全区/刘海仍待 Honor 90 Pro / iPhone 验证。

## 6. 维护

- 新增 UI 元素时，先回答：它在哪个 Canvas 下？尺寸用参考单位还是屏幕像素？H5 还是 Unity？
- 任何用 `Screen.width/height` 做**视觉尺寸**的代码都要单独审查；输入灵敏度用屏幕像素是另一回事。
- 每个里程碑收口前把本表跑一遍，截图进 `docs/evidence/`。
