## 0. 结论（先看）

- **没有发现会立刻中断游戏流程的 P0 逻辑缺陷**。状态机、统一 3-2-1、暂停/取消、结算只发一次、
  H5 壳状态机、存储迁移的行为与文档口径一致，事件订阅/退订成对，热路径没有明显的每帧字符串分配。
- **当前 WIP 有 1 个“跑不起来”的产物状态（P0）**：新 H5 要求 `protocol===3`，但入库的 `web/unity`
  是 protocol 2 的 1.0.0 产物。这是交接里已知的暂存安排，不是代码 bug，但会挡住 H5 验收、干净克隆和演示。
- **9 个 P1 风险**（旧 H5 难度丢失、旧 E2E 集体失效、perf 脚本跑不了、证据与代码不同步、权威文档漂移等）。
- **约 24 个 P2 清理项**（死成员、死资源、过期注释、日志噪声、测试脚本卫生）。
- 统计：P0 ×1、P1 ×9、P2 ×24（不含“不建议做”的条目）。

### 不建议做的事（防止这次整理变成新的重构）

- 不拆 `GameManager`/`WebGLBridge` 的类边界、不引 DI/事件总线/第三方包。
- H5 不引 TS/打包器/ES module：现在是三个 `<script>` 直加载 + `?v=` 缓存串，改造收益低于风险。
- 不动 `GameState` 枚举、线格式、`MapToWire`、计分公式、场景生成方式（都已验收/有协议契约）。
- 不重命名已验收的字段（`_reported`、`_applyingRemoteDifficulty` 等），只清理真正无引用的成员。
- 不为“目录好看”搬 `Assets/Scripts` 子目录：`SceneSetup` 用类型名生成组件，搬目录不会坏，但会制造无意义 diff。

### P1-8 点击坐标表对 `Screen.width` 的假设未验证（DPR 场景）（状态：未做，优化记录 U-04）

- `tools/e2e/ui-layout.mjs:15-23` 用 **canvas 的 CSS 宽高**决定 640×360 / 1280×720 分支；
  `HudCanvasScaler.cs:21-22` 的注释却假设 `Screen.width` 是**设备像素**（CSS × DPR，上限 2）。
- 现有测试一律 `deviceScaleFactor: 1`，所以两种解释结果相同，**测不出差别**。
- **风险场景**：768×1024 平板竖屏（canvas CSS 约 744 → 脚本按 640 参考；若 Unity 的 Screen.width 是 1488
  → 实际用 1280 参考）。点击点会偏。
- **建议**：先做一次实测（真机/DPR=2 的 768×1024 视口，把 `Screen.width` 打到 console），
  再决定：让脚本接收 `window.devicePixelRatio` 并按 Unity 真实语义换算，或把 Unity 的阈值改成读
  `canvas.clientWidth`（若 API 拿得到）。在结论出来前，测试矩阵里**不要**声称覆盖了 DPR>1 的窄平板。

### 3.6 性能线索（41.4 KB/s 分配）

- 逐行核对热路径后，**没有找到每帧字符串/数组/闭包分配**：`HudView` 只在整数变化建串；`GameManager` 只推事件；
  `EnemyAI` 全 struct 数学；`EnemySpawner` 网格/邻居缓冲复用；TMP 只在文本变化时重建。
- `PlayerHealth.TakeDamage` 每次扣血 `Debug.Log`（`PlayerHealth.cs:58`）是正常游玩里的分配源，但 40 只压测开了
  `invincible=1`（`docs/evidence/m6-refactor/perf-40.json`），不会走到这里。
- 因此 41.4 KB/s 更像引擎/物理/浏览器内部（40 个 Trigger 的物理回调、WebGL 事件桥）或 `GC.GetTotalMemory`
  采样本身的噪声，而不是本项目 C# 的显式分配。
- **建议的下一次压测实验**（只做对照，不改玩法）：同一构建依次跑 `enemyLimit=0 / 20 / 40`（都 `invincible=1`），
  看 `steadyAllocKBps` 是否随敌人数线性增长；若 0 只也有 ~40 KB/s，就把它记成“引擎基线”，不再追。
