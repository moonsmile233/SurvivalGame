## 2. 写前重读（文档热更新）

把上下文里的文件内容当成**缓存**，磁盘才是事实来源：

1. 写前 `jj status` + `Read` 目标文件。如果内容和你记的不一样，**丢弃草稿**，按磁盘版本重写。
2. 关键文档顶部有版本行：
   `> 文档版本：YYYY-MM-DDTHH:MM+08 · 作者：军师/执行方 · 改前必须从磁盘重读`
   版本行变了 = 内容变了，重新读。
3. 写后 `jj diff --stat <file>`，把"改了哪个文件 + 版本时间"写进汇报。
4. 另一个 Agent 在下一次动作前必须重读，不要继续用旧上下文。
5. 工具报 "file has been modified since read" 时，**不要绕过**：重新 Read 后再写。

## 3. 存档节奏（jj + GitHub）

### 3.1 每个逻辑步骤一个提交

相机、拥挤修复、压力曲线、素材、E2E 各自一个；**不要 A + B0 + B1 塞一个**。

```bash
# 完成一个步骤、构建/自测通过后
jj describe -m "feat(m4-b1): 拥挤修复（位置修正 + 停距/站位环）"
jj bookmark set wip -r @
jj git push --bookmark wip
jj bookmark set main -r @
jj git push --bookmark main
jj new                     # 开下一步；上一步成为 @-
```

- **`main` 只放已验证的检查点**；**`wip` 放最新工作状态**，允许未验收，用于 GitHub 备份。
- 步骤还没验证但想先存 GitHub：只推 `wip`，不动 `main`。
- 频率：**每完成一个子步就 describe + new；每次构建/自测通过就推 wip；每个绿检查点推 main**。
- **最少节奏**：一个子步最多配一次构建；连续工作超过 45 分钟还没有 checkpoint，就先 `jj describe` + 推 `wip`。
- 不要"改一大堆再存一个"；也不要把失败状态推到 main。
- 注意：jj 每个命令都会自动快照工作区，但**只有 `describe`/`new` 之后才是可读的历史**；
  不要依赖自动快照，也不要把所有东西留在同一个空描述的 `@` 里。
- 推送前 `jj git fetch`；远端有分叉就停，报告，**禁止 force push**。
- 代理不通/推送失败：按 CLAUDE 规则停下报告，不要改直连。

### 3.2 失败/半成品

- 用 `jj undo` 或 `jj restore` 回退；不要用 force push 掩盖。
- 一个步骤连续两次构建失败：先 `jj describe` 成 `wip: ...` 存住现状，报告卡点，不要继续叠加。

### 3.3 共享工作副本的提交隔离（2026-10-31 两次撞车后新增）

两个 Agent 共用一个工作副本，**对方的未提交改动随时会出现在 `@` 里**。禁止对整块 `@` 直接
`describe` + push；只提交自己的文件：

1. 写下一条前先 `jj status`；如果出现不属于你的文件，**不要整块 describe**。
2. 把自己的文件单独提出来：
   ```bash
   jj new                                  # @ 变成新的空提交，混合改动留在 @-
   jj squash --from @- --into @ <对方的文件…>   # 只把对方的文件搬进新 @，留在工作区
   jj describe -r @- -m "..."              # @- 现在只剩你的文件
   jj bookmark set wip -r @- && jj git push --bookmark wip
   ```
   对方的文件留在新的 `@` 里，不要动、不要提交。
3. 反过来（先让对方提交代码）同理：选中的是对方的文件，自己的留在工作区。
4. 如果已经整块提交并推到 origin：**禁止 force push**；由文件 owner 做一个清理/还原提交，
   在提交消息里写明“清理误入的构建产物/文件”。
5. 提交前后各看一次 `jj status`；时间窗很小时，先发一句“我要提交 docs，工作区先别动”，再操作。
