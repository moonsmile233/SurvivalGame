## 1. 权威顺序（冲突时按这个）

1. **代码与资产**：`Assets/Scripts/**`、`Assets/Configs/**`、`web/**` —— 数值/行为的最终事实。
2. **`docs/实现总览.md`** —— 当前玩法、状态、输入、敌人、UI、构建的汇总说明（本文档是它的入口）。
3. **`docs/bridge-protocol.md`** —— H5 ↔ Unity 接口契约（程序 owner）。
4. **`docs/architecture.md`** —— 代码结构与模块职责（程序 owner）。
5. **`docs/测试计划.md` + `docs/acceptance.md`** —— 怎么测、测过什么。
6. **`docs/项目规范.md`** —— 早期设计规范与背景，**部分内容已被实现总览取代**，只作为“为什么这样做”的依据。
7. **`docs/M*-执行记录.md` / `docs/evidence/**`** —— 历史证据，不改写。

## 3. 按目的读

- **第一次接触项目**：`实现总览` → `README` → `bridge-protocol`。
- **改玩法/数值**：`实现总览` §2/§3/§5 → 对应 ticket → `GameConfig`/`EnemyDefinition`。
- **改 H5/入口/暂停/全屏**：`实现总览` §3/§6 → `参考拆解` §2.4/§2.5 → `体验审查`。
- **改桥接**：`bridge-protocol` → `architecture` §3 → `WebGLBridge.cs` / `web/js/bridge.js`。
- **验收/发布**：`测试计划` → `acceptance` → `部署与托管` → `M5.md`。
- **查历史决策**：`M*-执行记录`、`玩法增强`、`项目规范`、git/jj 历史。

## 4. 维护规则

- 数值/行为改了：先改代码，再同步 `实现总览` 与 `README`/`acceptance`（按 owner）。
- 新玩法/新 UI/新流程：先更新 `参考拆解`（按设计对象选 2～3 个来源），再写 ticket。
- 新发现的体验问题：先记 `体验审查`，再决定是否进 ticket。
- 已完成/过期的设计：不要删除历史，标“历史/已被取代”，并指到当前文档。
- 文档顶部版本行变了 = 内容变了；写前从磁盘重读（见 `协作协议`）。
