# M4.6 — 暂停/恢复语义 + 继续倒计时 + 结算呈现（交付前 P0）

> 文档版本：2026-10-31T18:35+08 · 作者：军师 · 改前必须从磁盘重读；上下文旧副本作废。
> 触发：2026-10-31 用户 Honor 90 Pro 真机试玩；依据 `docs/参考拆解.md` §2.4/§2.5、`docs/体验审查.md` F1/F2/F3/F5/F14。
> 定位：M4 行为修正，**不阻塞 M5 交付**，但必须进最终构建；不改协议版本、不做主菜单/难度。

## 0. 结论（先看）

| 场景 | 现在 | 改为 |
|---|---|---|
| 切后台 / 窗口失焦 | 自动暂停；切回 **自动 3-2-1 后继续** | 自动暂停；切回**仍保持暂停**，不自动继续 |
| 点「继续」/ 按 P（玩家主动恢复） | 立即恢复 | **先 3-2-1 倒计时，再恢复**（手机有时间把手指挪回屏幕） |
| 恢复倒计时 3-2-1 | 只用于失焦自动恢复 | **保留**，但**只由玩家主动恢复触发**；自动恢复路径删除 |
| 失焦后切回 | 自动开始倒数 | 停在暂停面板，等玩家点继续；点完才倒数 |
| 暂停面板 | 只有「继续」 | 加「重新开始」（P1，见 §3） |
| 结算卡片 | 只滚到“最近边缘”，首屏常只露一半 | 完整滚入视野；重开按钮与结算同屏 |

**一句话**：失焦 = 暂停并保持；恢复 = 玩家主动点继续/按 P → 3 秒倒数 → 开始。

### 为什么保留 3-2-1

- 用户明确偏好：手机点「继续」时手还在屏幕外，需要 3 秒把手指移回触控区；桌面也可用来重新聚焦。
- 同类 Survivor-like（Brotato/20MTD）恢复是即时的，**3-2-1 是本作的刻意差异**，不是“行业标配”；
  只在玩家主动恢复后出现，不打断失焦流程。
- 浏览器游戏的通行要求是“恢复必须由用户手势触发”（见 `参考拆解 §2.5`），这一条已满足。

## 1. P0：暂停/恢复流程（必做）

### 1.1 Unity 状态与事件

- `WebGLBridge.SetPausedByVisibility`：
  - `"true"`：Playing → `PauseGame()`，置 `_pausedByVisibility = true`；
    若当前处于 Paused 且正在倒计时 → 调用 `CancelCountdownResume()`（停表、保持暂停）。
  - `"false"`：只清 `_pausedByVisibility`；**不调用 `RequestCountdownResume()`、不 `ResumeGame()`**。
    状态保持 `Paused`，等玩家操作。
- `GameManager`：
  - 保留 `RequestCountdownResume()` 与 `OnResumeCountdownRequested` 事件，但语义改为**玩家主动恢复请求**；
    由 `PausePanel` 的「继续」和 `PauseHotkey` 的 P/Esc 调用。
  - 保留 `CancelCountdownResume()` / `OnResumeCountdownCancelled`：倒计时中再次失焦、重开、状态离开 Paused 时停表。
  - 倒计时结束由 `PausePanel.Update()` 调 `ResumeGame()`（现有实现，保留）。
- `PauseHotkey`：
  - Playing → `PauseGame()`；
  - Paused → `RequestCountdownResume()`，**不要直接 `ResumeGame()`**；
  - 倒计时进行中再按 P/Esc：忽略（不加速、不取消；避免误触）。
- `WebGLBridge.ResumeGame`（H5 指令，目前无人调用）：若保留，也改为请求倒计时，不直接恢复。
- `PausePanel`：
  - 「继续」按钮：从 `ResumeGame` 改为 `RequestCountdownResume`；
  - 倒计时期间隐藏标题与「继续」，显示 3/2/1（现有实现保留）；
  - 倒计时结束 `ResumeGame()`；离开 Paused 时 `StopCountdown()`（现有实现保留）。
- 不要新增状态；`Paused` 仍是唯一暂停态。倒计时是 Paused 内的表现，不是新状态。

### 1.2 H5

- `web/js/app.js` 的 `Paused` 文案改为：
  - 触屏：`已暂停 · 点「继续」，3 秒后开始`
  - 桌面：`已暂停 · 点「继续」或按 P，3 秒后开始`
- 删除「切回后 3 秒继续」这类暗示“自动恢复”的文案；明确是**玩家点了才倒数**。
- `blur/focus/visibilitychange` 去重逻辑保留；失焦只发 `"true"`，切回只发 `"false"`。

### 1.3 失焦残留输入（P1，先测再改）

浏览器/Unity 的常见坑：按住方向键失焦、在别的窗口松开，切回后可能仍判定为按住；
触摸在切后台时也可能留下锚点。处理：

- 先按 §1.4 用例实测；能复现再改，不要凭空加代码。
- 若复现：
  - `TouchInput` 增加 `ResetState()`：`_fingerId = -1`、`_mouseTracking = false`、`_move = zero`；
  - `PlayerInputSource` 增加 `virtual void ResetState()`，`PlayerInputRouter` 转发；
  - 进入 Paused / 开始倒计时时调用一次；键盘侧若仍复现，再考虑“失焦后忽略键盘直到所有键抬起”。
- 桌面切回首帧的时间尖峰：已有 `Time.maximumDeltaTime = 0.1f` 与倒计时 `MaxCountdownStep = 0.1f`；
  在 §1.4 的长时间切后台用例里确认没有瞬移/掉血。

### 1.4 测试（必须真实失焦）

- 桌面 Chrome：
  - 开始 → 手动暂停 → 点继续/按 P → 看到 3-2-1 → 恢复 Playing；
  - 开始 → Alt-Tab 失焦 → 显示暂停 → 切回 → **仍是暂停** → 点继续/按 P → 3-2-1 → 恢复；
  - 倒计时中再次 Alt-Tab → 倒计时停止、保持暂停；切回后需重新点继续；
  - 按住 D 不放 → Alt-Tab → 在别的窗口松开 D → 切回 → 点继续 → 3-2-1 结束后玩家不应持续向右走；
  - 切后台 30 秒再回来：时间/位置无跳变，倒计时没有“一帧走完”。
- 手机 390×844 / Honor 90 Pro：
  - 开始 → 切到别的 App → 回来 → 仍是暂停 → 点「继续」→ 3-2-1 → 恢复；
  - 点继续时手在屏幕外，3 秒内把手指移到触控区，倒计时结束能马上拖动。
- Ready / 结算状态失焦：不误触发暂停或倒计时。
- console 0 error；E2E 更新：删除“切回自动恢复”断言，改为
  「切回仍 Paused → 点继续 → 倒计时出现 → Playing」。

## 2. P0：结算呈现（必做）

现状：`onGameOver` 用 `scrollIntoView({ block: 'nearest' })`，卡片比视口高时只滚到最近边缘，
1280×720 上常见“只露出结算卡片的上半截”（证据：`e2e-online-chrome-desktop-result.png`）。

改法（H5 only，优先 A）：

- **A（推荐，最小改动）**：`block: 'start'`，让结算卡片顶部对齐视口；确认「重新开始」按钮与卡片同屏。
  390×844 竖屏与 1280×720 各截一张。
- **B（更彻底）**：结算卡片改为覆盖在游戏区上的 overlay（半透明背景），画布不滚走。
  卡片高度超过游戏区时允许卡片自身滚动。工作量大一点，先不做。

验收：

- 390×844、844×390、1280×720 三种视口，结算后不用手动滚动就能看到：胜负、本次得分、最高分、昵称、存活、重新开始。
- 连续重开 3 次仍正常。
