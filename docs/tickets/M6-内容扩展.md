## 0. 目标 / 非目标

**目标**：把现在的「1 种敌人 × 1 档难度 × 存活分」扩展成「3 种敌人 × 3 档难度 × 有技巧表达的计分」，
同时保持 60 秒单局、同屏 ≤20、移动端可玩、作业 17 条全绿。

**非目标**：攻击/武器/道具/商店/Boss/远程弹幕/排行榜/账号/跨刷新存档。

**硬边界（2026-11-01 用户重申，不可越线）**：
- **玩家没有任何攻击手段**（无挥砍、无武器、无技能、无击杀）；所有玩法仍是“躲避 + 走位”。
- **敌人没有远程手段**（无投射物、无弹幕、无召唤）；敌人伤害只来自**接触**与**冲锋冲刺**两种近身判定。
- 计分、难度、敌人设计都不得引入“击杀”概念；挥砍只是可扩展性示例，本票不做。
- 若以后要加攻击，必须先改 `项目规范` 与 `bridge-protocol`，另开票，不在 M6 内夹带。

**需求核对（2026-11-01）**：原始需求 H5 部分只写「H5 显示本次成绩和历史最高分；最高分使用 localStorage 保存」，
**没有排行榜**（`项目规范` §原文）。排行榜需要后端/账号/防作弊，属于新增系统，本票不做；
若要做，先确认是“本机历史记录（localStorage top N，轻）”还是“跨玩家排行榜（需服务端，重）”，另开票。

## 2. H5 主界面（D1=推荐方案）

布局自上而下：标题 → 一句话规则（存活 60 秒）→ 昵称 → 难度三卡 → 当前难度最高分 → 开始游戏 → 全屏 → 操作提示。

- 难度卡：名称 + 一句话（例如「敌人更慢、更少」/「标准」/「敌人更快、更多」）+ 得分倍率 `×1.0 / ×1.3 / ×1.6`。
  默认普通；选择记 `localStorage["survival.difficulty"]`。
- 最高分分档：`survival.bestScore.easy|normal|hard`；旧键 `survival.bestScore` 迁移到 `normal`（只迁一次）。
- **开始 = 1 次点击进游戏**；进入 Playing 后难度锁定；结算显示本局难度与同难度最高分。
- 全屏：**Ready 下也可用**（同时修复「全屏时隐藏开始/难度区」的问题）；Playing/Paused 保持现有行为。
- 响应式：320×568 / 390×844 / 844×390 / 1280×720 不溢出、不重叠；按钮 ≥44 CSS px（短横屏 ≥36）。

验收：
- 三档可选、可开始，难度进入 Unity 后生效；刷新记住难度与分档最高分；
- Ready 全屏下能看到并点击开始/难度；console 0 error；6 视口矩阵重跑。

## 3. 多种敌人（D2=3 种）

### 3.1 类型表

| 类型 | 靠近速度 | 行为 | 伤害 | 测试的玩家技巧 |
|---|---|---|---|---|
| 追击 Chaser | 1.8 | 现行：追到站位环/停距，接触伤害 | 12 | 基础走位 |
| 冲锋 Charger | 1.5 | 距玩家 ≤4.5 → **前摇 0.45s**（变色 + 缩放）→ **锁定方向**直冲 0.45s、速度 5.0 → 恢复 0.8s → 冷却 1.5s | 冲刺 15 / 平时接触 12 | 横向闪避、不站直线 |
| 绕行 Flanker | 1.9 | 目标点 = 玩家侧后方 2.4；距 ≤1.2 直接扑；侧绕 6s 未切入则转为直追 | 12 | 变向、防被包围 |

规则：
- 冲锋方向在**冲刺开始时**锁定，冲刺中不转向；玩家侧步可躲（参考 b.mphilley「前摇 + 固定路径 + 激活后可躲」）。
- 冲刺撞地图边界提前结束；冲刺期间跳过两两分离修正（避免被推挤打断）；同一次冲刺最多结算一次伤害（无敌帧仍生效）。
- 不新增素材：用颜色 + 尺寸 + 前摇缩放区分；正式素材另议。
- **敌人无远程**：冲锋/绕行都只做近身判定（接触/冲刺），不产生任何投射物。
- 同屏总上限 20（简单 14），回收规则不变。

### 3.2 生成配比

普通：
- 0–15s：追击 100%
- 15–35s：追击 75% / 冲锋 25%
- 35–60s：追击 55% / 冲锋 30% / 绕行 15%

简单：冲锋 25s 起、绕行 45s 起（权重更低）；困难：冲锋 10s 起、绕行 25s 起（权重更高）。
权重进难度配置，不写死在 Spawner。

### 3.3 验收

- 三种同屏可分辨；冲锋前摇可读、玩家能躲开；绕行不长期贴脸；
- 20 只不抖动、无每帧 GC；WebGL 包体增长 ≤0.3MB；中端手机 ≥30 FPS（真机）。

### 3.4 同屏上限与性能（2026-11-01 用户：土豆兄弟几百只都能跑，我们 20 就有问题）

**为什么 Brotato 能同屏几百只，我们 20 就有压力？** 不是“Unity 不行”，是四层成本叠加：

| 层面 | Brotato（原生 Godot） | 我们（Unity WebGL） |
|---|---|---|
| 运行平台 | 原生客户端，多线程、无浏览器沙箱 | 浏览器单线程 WASM，CPU 开销约为原生 2～5 倍；移动端还会降频/节流 |
| 接触判定 | 基本不用逐对象刚体/碰撞体，简单距离或网格 | 每只敌人挂 `Collider2D + Rigidbody2D`，靠 Physics2D Trigger 判伤害；数量上来后 broadphase + 回调成本高 |
| 更新模型 | 统一循环 + 池化，单实体逻辑很轻 | 每只一个 MonoBehaviour `Update`，每次更新跨托管/原生边界 |
| 生成方式 | 池化复用，几乎无 GC | `Instantiate/Destroy`，生成/销毁有 GC 尖峰 |

结论：**20 不是引擎上限，是没压测过的保守预算**。以现有实现先做下面几项优化，桌面 60～100、中端手机 30～50 是现实目标；
但最终数字必须以 Honor 90 Pro 实测为准，不靠猜。

**优化顺序（按性价比，每步单独压测 + 回归）**：

1. **接触判定改手写距离检查**（玩家 vs 敌人 O(n)），敌人不再挂 `Rigidbody2D/Collider2D`——最大头。
2. **敌人对象池**：预生成、复用、禁用而不是 Destroy；消除生成/销毁 GC。
3. **分离修正用均匀网格**（cell ≈ 1.0，只查相邻 9 格），O(n) 代替 O(n²)；100 只也只有几百次比较。
4. **AI 降频**：移动/寻路 20Hz、渲染 60Hz、位置插值；单线程下省 CPU 明显。
5. 仍不够才考虑统一 `EnemyManager` 遍历（去掉每对象 Update）——改动最大，放最后。

**让上限不可感知**（无论最终数字）：到顶时**回收最远/视野外的敌人并立即补位**，而不是跳过生成；
远处回收从 3 秒降到 1.5 秒；压力来自速度、组合和出怪节奏，不是堆数量。上限只当安全阀。

**验收**：
- 压测表：20 / 30 / 40（优化后再加 50 / 80），桌面 Chrome + Honor 90 Pro，记录 FPS p95、GC、内存；
- 目标：Honor 90 Pro ≥30 FPS、桌面 ≥60 FPS；据此定基准上限（目标普通 30～40、困难 50）；
- 正常游玩中玩家看不到“刷怪停止”；17 条与其他门禁全绿；`Update` 稳定后无每帧 GC。

## 4. 难度（D3=3 档）

| 参数 | 简单 | 普通 | 困难 |
|---|---|---|---|
| 敌人速度倍率 | 0.90 | 1.00 | 1.10（总上限 2.2 仍适用；冲锋 5.0×1.1=5.5） |
| 生成间隔倍率 | 1.20 | 1.00 | 0.85（下限仍 0.5s） |
| 伤害倍率 | 0.80 | 1.00 | 1.15 |
| 同屏上限 | 14 | 20 | 20 |
| 冲锋 / 绕行解锁 | 25s / 45s | 15s / 35s | 10s / 25s |
| 压力曲线终点 | 1.10 | 1.15 | 1.20 |
| 计分倍率 | 1.0 | 1.3 | 1.6 |

- 数据进 `DifficultyProfile`（ScriptableObject 或 `GameConfig` 子结构），代码只读，不写 `if` 分支。
- 胜利条件三档一致：存活 60 秒。
- 目标体感：**简单** 2～3 局内能赢（给第一次玩/面试官随手玩）；**普通** 熟悉后胜率约一半（默认档）；
  **困难** 首局大概率输，熟练后能偶尔赢。达不到就先调数值，不加快捷难度。
- 验收：切换难度重开后参数生效；5 局/档基线记录胜率与首次受击秒数。

## 5. 计分改造（D4：去掉擦身，存活分分段加速）

**设计理由**：每秒固定 10 分太机械——早死和晚死的边际收益一样，玩家感受不到“越到后面越紧张”。
改成**每 15 秒提一档每秒得分**：早期不惩罚新手，后期让“再撑一会儿”明显更值钱；分数跳字也会加速，观感更活。

```
计分粒度：每 0.1 秒结算一次（用户 2026-11-01：不要“每秒 +10”的跳字，要 0.1 秒 +1 的连续感）

存活分（按生存时间分段累计，每 0.1 秒加分）：
  0–15s   每 0.1s +1.0 分（=10/秒）   → 满段 150
  15–30s  每 0.1s +1.2 分（=12/秒）   → 满段 180
  30–45s  每 0.1s +1.5 分（=15/秒）   → 满段 225
  45–60s  每 0.1s +2.0 分（=20/秒）   → 满段 300
  满 60 秒合计 855

血量分 = 结算剩余 HP × 1（0～100）

基础分 = (存活分 + 血量分) × 难度倍率（1.0 / 1.3 / 1.6）
最终分 = round(基础分) + 胜利奖励 200（固定，不乘倍率）
```

- 实现：内部用 float 累计，每 0.1 秒把当档速率加进去；HUD/结算显示整数（向下取整），不出现小数。
- 若用户坚持全程固定每 0.1 秒 +1（60 秒 = 600），则取消分段、只保留血量分与难度倍率；**推荐保留分段**，
  否则满分太容易达到，和“最高分要有区分度”的目标冲突。

参考结果（结算卡会按这个展示明细）：

| 结果 | 简单 | 普通 | 困难 |
|---|---|---|---|
| 15 秒阵亡、剩 70 HP | 220 | 286 | 352 |
| 30 秒阵亡、剩 50 HP | 380 | 494 | 608 |
| 60 秒胜利、满血 | 1155 | 1442 | 1728 |

- 结算卡：本次得分 / 同难度最高分 / 难度 / 存活秒数 / 受击次数 / 新纪录。
- **不做擦身分**（用户 2026-11-01 决定）：判定与玩家理解成本高，收益不如把存活曲线做好。
- **计分不含击杀**：玩家无攻击手段，`ScoreService` 的击杀字段不参与公式、不显示；
  `项目规范` §6.1 的“击杀分 ×20”随本票作废（实现时同步改文档）。
- 分段只影响“每秒得分”，不改 HUD 的剩余时间显示（仍按秒倒计时）。
- 验收：同样表现下三档分数按倍率不同；受击越少分越高；60 秒满血普通局 = 1442；
  胜利奖励只加一次；最高分按难度隔离；刷新仍在；分段边界（15/30/45 秒）计时准确。
- **分数上限与“满分”**：当前理论上限 = 困难 60 秒满血 1728（普通 1442、简单 1155）。不设“满分”概念；
  5 局基线要验证困难满血流获胜是少数（目标 <20%），否则调难度而不是调分。最高分按难度分档，避免简单档刷满。
  难度倍率先用 **1.0 / 1.3 / 1.6**，不提前拉大；等 5 局/档测试后再决定是否改成 1.0/1.4/1.8（用户 2026-11-01：先观察）。
