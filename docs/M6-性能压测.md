> 作者：程序 · 状态：**桌面 20/30/40 已出 + 拥挤修复已验收（桌面）；真机 cap40 已测（修复前构建），真机 20/30 与修复后复测待跑**
> 依据 `docs/tickets/M6-内容扩展.md` §3.4 / §7
> 结论先行：**桌面（RTX 4060 Ti / Chrome / 165Hz）20/30/40 均 165 FPS、p95 7ms；真机 Honor 90 Pro cap40 稳态 113 FPS / p95 14ms**，
> 两端都不是瓶颈。拥挤（玻璃球互推）已修：40 只围住静止玩家时 40/40 站定、位移 0、两帧像素差 0。
> **默认上限是否从 20 提高，等真机 20/30 补测 + 修复后真机手感复测再定。**

## 1. 测什么、怎么测

只测**现状**（未做任何优化）：敌人上限 20 / 30 / 40，其余数值、生成曲线、两两修正、物理判定全部不变。

用 URL 参数覆盖（同一个构建跑完三档，避免"测的是哪一版"）：

| 参数 | 值 | 作用 |
|---|---|---|
| `perf=1` | 开 | 创建 `PerfProbe`（普通 URL 不创建，默认行为不变） |
| `enemyLimit` | 20 / 30 / 40 | 覆盖同屏上限 |
| `roundDuration=600` | 600 秒 | 延长回合，避免 60 秒结算打断稳态采样 |
| `invincible=1` | 开 | 玩家不受伤（站着不动才能稳定维持高同屏数量） |
| `perfSeconds=90` | 90 秒 | 第 90 秒打 `[PERF-SUMMARY]` |

采样口径（`Assets/Scripts/Core/PerfProbe.cs`）：

- **帧时间**：`Time.unscaledDeltaTime`，只在 Playing 累计；每 2 秒一个窗口，p95/p99/max 取窗口内分位。
- **稳态**：最后 20 秒（且只取到顶之后）。
- **分配**：`GC.GetTotalMemory(false)` 的正增量/秒（负增量是回收，不计）——GC 压力的直接代理。
- **内存**：托管堆（`GC.GetTotalMemory`）+ WASM 线性内存（jslib 读 `HEAPU8.length`）。
- **GC 次数**：`GC.CollectionCount(0)`（IL2CPP 下可用，已确认有增长）。

桌面跑法：`tools/e2e/perf.mjs`（Playwright 有头 Chrome，**窗口移到屏幕外** `-32000,-32000`，
并关闭 occlusion/后台节流；无头 SwiftShader 的数据不作数）。

环境：Windows 11 · Chrome 156 · RTX 4060 Ti（ANGLE D3D11）· 165Hz · 画布 936×527 · DPR 1

| 上限 | 到顶(s) | 稳态敌人数/站定 | FPS | p95 | p99 | max | 稳态分配 | 全程分配 | 托管堆 | WASM 内存 | 站位抖动 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 20 | 27.0 | 20 / 20 | 163.6 | 7ms | 7ms | 67ms* | 40.6 KB/s | 3.76 MB | 2.2 MB | 55.4 MB | 0 u/s |
| 30 | 37.9 | 30 / 30 | 165 | 7ms | 7ms | 8ms | 40.8 KB/s | 3.76 MB | 2.2 MB | 55.4 MB | 0 u/s |
| 40 | 47.2 | 40 / 40 | 165 | 7ms | 7ms | 7ms | 41.0 KB/s | 3.77 MB | 2.2 MB | 55.4 MB | 0 u/s |

\* cap20 的 67ms 是一次孤立尖峰（p99 仍 7ms），cap30/40 没有复现；后续优化时继续留意生成瞬间。

证据：`docs/evidence/perf-local-chrome-desktop-cap{20,30,40}.json` + 同名 `.png`/`-b.png`（两张间隔 5 秒）
+ `-diff.png`（裁剪区差异热力图，三个上限都是 0 像素差）。截图里能看到 `时间 08:00`、生命 100/100、站位成型。

> 修复前（构建 `07:22:19Z`）同一套参数是 165 FPS / p95 7ms / 4.1MB，**性能数字几乎一致**；
> 差别在行为：修复前 40 只时站定 37 只、持续有约 0.23 u/s 的残余移动，修复后 40/40 站定、0 u/s。

**读法**：

- 165 FPS 是 vsync 上限（165Hz 屏），p95 7ms 说明**没有任何一帧掉出 vsync**；三档数字几乎一样，
  说明 40 只时桌面仍有大量余量，桌面不能用来判断上限。
- 全程分配约 4.1 MB 集中在**填充期**（每 2 秒一只 `Instantiate` + `AddComponent` + `Collider2D/Rigidbody2D`），
  到顶后稳态分配只有约 45 KB/s（HUD 字符串等零碎）——**对象池要解决的是填充期 GC 尖峰**，
  不是稳态帧率。
- cap=20 的 max 16ms 是一次孤立尖峰（生成/首次窗口），cap 30/40 没有复现；后续优化时留意生成瞬间。

## 3.1 复测用的真机步骤（20/30 补测）

我这台机器没有可用真机，需要人工用手机跑同一构建（本地静态服务已在 `192.168.1.100:8000`）。

**步骤**（每档一条 URL，共 3 次）：

1. 手机连同一个 Wi-Fi；用 Chrome **无痕标签页**打开（避免缓存旧包）。
2. **横屏**（与真实游玩一致，竖屏游戏区只有约 220px 高，测出来的帧率没有参考价值）。
3. 点「开始游戏」（H5 的按钮；Unity 侧已经带 `perf=1`，会自动创建探针）。
4. 等左上角叠层出现 `--- DONE 可截图 ---`（约 95～100 秒；cap40 也在这个时间出 DONE）。
5. 截图整屏发回。中途不要切 App（切走会按设计自动暂停、采样停止；真断了就点「继续」走 3-2-1）。

URL：

```
http://192.168.1.100:8000/?perf=1&enemyLimit=20&roundDuration=600&invincible=1&perfSeconds=90&overlay=1
http://192.168.1.100:8000/?perf=1&enemyLimit=30&roundDuration=600&invincible=1&perfSeconds=90&overlay=1
http://192.168.1.100:8000/?perf=1&enemyLimit=40&roundDuration=600&invincible=1&perfSeconds=90&overlay=1
```

叠层（`web/js/perf-overlay.js`，只在 `perf=1&overlay=1` 生效）会显示：实时 `alive / fps / p95 / alloc / heap / wasm`，
90 秒后追加 `DONE` + 稳态 20 秒的 `fps / p95 / p99 / alloc`。桌面已用同一页面验证过显示正常
（`docs/evidence/perf-local-chrome-desktop-cap20-overlay.png`）。

判定标准（M6 §3.4）：Honor ≥30 FPS。拿到三档数据后再决定默认上限（目标普通 30～40、困难 50）。

## 4. 局限（读数据时注意）

- `roundDuration=600` 会同时拉平 `EnemyAI` 的压力曲线（速度从 1.0→1.15 摊到 600 秒）。
  对"同屏数量成本"影响很小，但不是逐帧等价于 60 秒局；后续复测可用「到顶后固定 60 秒」的方式再核对。
- `invincible=1` + 玩家站在原点：敌人聚成站位环并互相推挤，是最挤的情况；真实游玩中玩家会移动，
  帧成本只会更低，不会更高。
- 屏幕外窗口已与屏幕内对比过（cap20：屏幕内 165 FPS / p95 7ms，屏幕外同数字），没有被 Chrome 判遮挡。
- 桌面 FPS 被 165Hz vsync 卡住，**看不到 40 只时的真实余量**；要量化桌面余量得关 vsync，本步没做。

## 5. 拥挤修复（「玻璃球互推/微抖」，2026-11-01）

**现象**：敌人贴近后频繁小幅互推、像玻璃球挤在一起；40 只时更明显（用户真机与压测都能看到）。

**根因（改前代码）**：
- 站位只有 12 个固定槽位，20～40 只时一个槽位 2～4 只共享同一个目标点：走到位 → 被分离修正推开 →
  再走回去，形成每帧的极限环，就是看到的持续微抖。
- 分离修正是每帧 2 轮**顺序**两两修正（同一只可能被推两次）+ 无阻尼 + 无滞回，推过头再被拉回。

**改法**（`EnemySpawner` / `EnemyAI`，数值进 `GameConfig`）：
1. 站位改为**唯一槽位 + 分环**：环半径 = 基础停距 0.7 + ring × 间距 0.95，容量 = 周长/间距（4/10/17/23/…），
   同环角度均分、相邻环错开半格；槽位随回收释放，新敌人优先补内圈空位。
2. 分离修正：**20Hz + 均匀网格邻域（cell = 间距）+ Jacobi 累加 + 阻尼 0.45 + 滞回（< 0.9×间距才推）
   + 单次位移 ≤ 0.12**。
3. 任何一方已进入站位区（离自己的站位点 < 1.0）就跳过这一对：站位环是钉子，同时也不会挡住赶路的敌人。
4. 到达容差从 0.25 收紧到 0.10；到位的敌人本帧不再移动。

**踩坑（留档）**：第一版是"只让已站定的敌人不接收推力"（阈值 0.35），结果外环变成不可穿透的壳——
后到内圈的敌人在环外被反复推开，卡在 6.5 单位外（站定 36/40，`perf-local-chrome-desktop-cap40-crowdfix2.json`
里 `unsettledMax=6.51`）。改成"任一方在站位区就跳过整对、阈值 1.0"后消失（40/40）。别再把站位环做成有推力的实体。

**验收（40 只围住静止玩家）**：
- 探针稳态 20 秒：**40/40 站定，平均位移 0.000 u/s**（修复前 37/40、0.23 u/s，
  见 `perf-local-chrome-desktop-cap40-crowdfix.json`）。
- 两帧间隔 5 秒、裁掉 HUD 的游戏区像素差 **0**（`docs/evidence/perf-local-chrome-desktop-cap{20,30,40}-diff.png`）。
- 接触伤害仍只由最内环触发（外环是包围，不造成伤害）；敌人都是 Trigger，玩家可以直接穿出包围。
- 17 条回归：见 `docs/evidence/e2e-local-chrome-desktop-summary*.json`（本轮构建已跑）。
